# 仕様案: 階層マップ (システム関連図・状態遷移図・ER 図) とマップ文書

状態: **段階 1〜4 を実装済み** (階層マップ / データの流れ `flows` / マップ文書 `maps/` / ER 図) / 2026-10-18
段階 4 は 6 章の別の木 (`view: "er"`) ではなく、DB の箱の中にテーブルを置く形にした (システムとデータが 1 つの木でつながり、機能 → テーブルの読み書きがそのまま上の階層にまとまるため)。
MCP: `create_map` / `read_map` / `write_map` を追加し、`list_decks` / `audit_deck` / `screenshot_deck` / `open_deck` / `export_deck` / 履歴 / `upgrade_deck` はマップ文書にも使える。
閲覧の補助 (拡大縮小・ドラッグ移動・ミニマップ) と、MCP での部分的な読み書き (`read_map` の `outline` / `node`、`write_map` の `node` + `part`) も実装済み。
未実装: `copy_map_part`

## 0. 目的と背景

大きなシステムの関連図を「全体 → 細部 → 全体」と行き来しながら読めるようにする。
あわせて、**データがどのシステム・機能を通るのか**を、どの階層から見ても追えるようにする。

既存の `.diagram` (関連図・ズームマップ) には次の限界がある。

| 今の `.diagram` | 困ること |
|---|---|
| 入れ子は 1 段だけ。中身は親の箱の中に縮小して描く | 3 段以上の大きなシステムを描けない。深くなるほど文字が小さくなる |
| 戻る操作は「背景をクリック / Esc」だけで、今どこにいるかが表示されない | 深い階層で迷子になる |
| 矢印は同じ階層の中でしか結べない | 外側の `注文システム → 注文 DB` と、内側の `注文 API` がつながらない。データの流れが階層の境目で途切れる |
| スライドの中でしか使えない | 1920×1080 の 1 枚に収まらない大きな図・資料に向かない |

この案では、1 つのデータ形式 (階層マップ) と 1 つの描画部品を作り、次の 2 つの場所で使う。

1. **スライドの部品** (`.diagram` の拡張): 発表の中で全体から細部へ入って見せる
2. **マップ文書** (新しい文書の種類): スライドなしで、ブラウザ全体を使って全体から細部まで読む

ER 図と状態遷移図も同じ仕組みに載せる。

## 1. 考え方: 3 つの原則

1. **矢印は「一番細かい階層」で 1 回だけ書く。上の階層の矢印は自動で作る (集約)**
   `注文 API → 注文 DB` と書けば、全体図では `注文システム → 注文 DB` の矢印が自動で出る。
   上の階層と下の階層で同じ関係を 2 回書かなくてよいので、食い違いが起きない。
2. **中に入ったら、拡大した絵ではなく「その階層の図」を描き直す (意味のズーム)**
   入る瞬間だけカメラのズームで演出し、着いたら子の図を通常の大きさで描き直す。
   これで深さに制限がなくなり、どの階層でも文字の大きさが変わらない。
3. **中に入っても、外とのつながりを画面の端に残す (境界ノード)**
   `注文システム` の中に入ると、外の `注文画面` や `決済サービス` が左右の端に薄く出て、そこから矢印が内側の部品へつながる。
   どこから入って、どこへ出ていくデータかが常にわかる。

## 2. データ形式

### 2.1 全体

```jsonc
{
  "title": "EC サイト全体",
  "direction": "LR",
  "nodes": [ … ],          // 一番上の階層のノード。children で何段でも入れ子にできる
  "edges": [ … ],          // どの階層のノード同士でも結べる (id はマップ全体で一意)
  "flows": [ … ],          // 名前付きのデータの流れ (階層をまたぐ経路)
  "steps": [ … ]           // スライドで使うときの段階表示 (省略可)
}
```

### 2.2 ノード

```jsonc
{
  "id": "order.api",                  // マップ全体で一意。"親.子" の形を推奨 (必須ではない)
  "label": "注文 API",
  "sub": "Java / Spring",
  "kind": "service",                  // service (既定) / db / queue / user / ext / screen / batch / state
  "accent": true,
  "detail": "<p>説明 (HTML)</p>",     // クリックで詳細パネル
  "tags": ["個人情報"],               // 絞り込み・検索用 (マップ文書)
  "children": {                       // 中身。何段でも入れ子にできる
    "direction": "TB",
    "nodes": [ … ],
    "edges": [ … ]                    // ここに書いても、トップの edges に書いてもよい
  }
}
```

### 2.3 矢印 (データの流れの最小単位)

```jsonc
{ "from": "order.api", "to": "order.db", "label": "注文を保存", "data": ["注文"], "type": "sync" }
```

| 項目 | 意味 |
|---|---|
| `from` / `to` | ノード id。**階層が違ってもよい** (例: `web.cart` → `order.api`) |
| `label` | 矢印の上の文字 |
| `data` | 流れるデータの名前 (配列)。データで絞り込み・強調するのに使う |
| `type` | `sync` (実線) / `async` (破線・キュー経由など) / `read` (参照のみ) |
| `both` / `curve` / `style` | 今の `.diagram` と同じ |

#### 上の階層での見え方 (集約のルール)

表示中の階層で、矢印の両端を「今見えている祖先ノード」に置き換える。

- 置き換えた結果、両端が同じノードになる矢印は表示しない (中の話なので)
- 同じ 2 ノードの間に複数の矢印が集まったら 1 本にまとめ、本数を小さな丸 (例: `3`) で示す。ラベルは、1 本だけならそのまま、複数なら `data` を重複を除いて並べる (例: `注文・在庫`)
- まとめた矢印をクリックすると、もとの矢印の一覧を詳細パネルに出す (「どの機能とどの機能がつながっているか」)

### 2.4 データの流れ (`flows`)

業務の流れを、矢印の経路として名前を付けて登録する。階層をまたいでよい。

```jsonc
"flows": [
  { "id": "order", "label": "注文の流れ",
    "path": ["web.cart", "order.api", "order.stock", "stock.db", "order.api", "order.pay", "ext.pay"],
    "note": "カートから決済まで" }
]
```

- 流れを選ぶと、**どの階層を見ていても**その経路が光り、線の上を点が流れる (上の階層では集約した矢印が光る)
- 「流れを順に追う」ボタン (スライドでは → キー) で、1 区間ずつ進みながら、必要な階層へ自動で入ったり出たりする
- `path` の隣同士の間に矢印が書かれていなければ、警告する (`audit` の `flow` 項目)

### 2.5 段階表示 (`steps`。スライド用)

```jsonc
"steps": [
  { "note": "全体像" },
  { "at": "order", "note": "注文システムの中" },             // その階層へ入る
  { "at": "order", "flow": "order", "upto": 3, "note": "在庫を確認" },  // 流れの 3 区間目まで
  { "at": "", "focus": ["web", "order"], "note": "全体に戻る" }        // "" はトップ
]
```

今の `zoom` / `focus` / `flow` / `select` / `note` もそのまま使える (`zoom` は `at` の別名として扱う)。

## 3. 操作 (スライドの部品・マップ文書で共通)

| 操作 | 動き |
|---|---|
| 中身を持つノードをクリック | ズームしながらその階層へ入る |
| 中身のないノードをクリック | 詳細パネルを開き、つながる矢印を強調 |
| 矢印をクリック | 矢印の詳細 (まとめた矢印なら、もとの矢印の一覧) |
| 左上のパンくず `全体 › 注文システム › 注文 API` | クリックでその階層へ戻る |
| Esc / Backspace | 1 つ上の階層へ戻る (詳細パネルが開いていれば先にパネルを閉じる) |
| 端の境界ノードをクリック | その外のノードがある階層へ移る (隣のシステムへ渡り歩く) |
| 右下の「流れ」ボタン | 登録したデータの流れの一覧。選ぶと強調、▶ で順に追う |

### 中に入ったときの画面

```
┌ 全体 › 注文システム ─────────────────────────────────────┐
│                                                          │
│  ┊注文画面┊ ──注文──▶ [注文 API] ──▶ [在庫チェック] ──▶ ┊在庫 DB┊ │
│   (境界)                 │                          (境界) │
│                          └──▶ [決済連携] ────────▶ ┊決済サービス┊│
│                                                          │
│ 説明バー: 注文システムの中                    [流れ ▾]     │
└──────────────────────────────────────────────────────────┘
```

- 境界ノードは、表示中の階層の外にあり、中の部品と矢印でつながっているもの。外の一番近い「見えている祖先」の名前で出す
- 境界ノードは入ってくるものを左、出ていくものを右 (TB なら上・下) に置く。両方向なら入ってくる側

## 4. スライドの部品として (`.diagram` の拡張)

新しいクラスは作らず、**`.diagram` を拡張する** (AI が迷わないよう、部品は 1 つにする)。

- 入れ子が 2 段以上、または `"drill": true` のとき、上の「入って描き直す」動きになる
- 入れ子が 1 段で `drill` がないときは、今と同じ (親の箱の中に縮小表示してズーム)。**既存のデッキはそのまま動く**
- 1 つの階層に置くノードは今と同じく 12 個程度まで。超えたら `Deck.audit()` が `overflow` ではなく `density` (新しい種類) で知らせる
- PDF・一覧: その時点のステップの階層を静止画で出す。`"print": "all"` を付けると、各階層を 1 枚ずつ書き出す (スライドが増える)

## 5. マップ文書 (スライドなしの資料)

### 5.1 位置づけ

デッキと同じく **1 ファイルの HTML** (エンジン・テーマ・ブランドを埋め込み、オフラインで動く) だが、16:9 のスライドではなく、ブラウザの画面全体を使う資料。
設計書・システム説明書・データ辞書を「地図アプリのように」読むためのもの。

### 5.2 画面

```
┌ ロゴ  EC サイト全体                         [検索 🔍] [流れ ▾] [データ ▾] ┐
├────────────┬────────────────────────────────────────┬──────────────┤
│ 目次 (階層) │                                        │ 詳細パネル    │
│ ▾ 全体      │   パンくず: 全体 › 注文システム          │ 注文 API      │
│   ▸ 画面    │                                        │ ─────────── │
│   ▾ 注文    │          (マップ本体)                   │ 説明・表・コード │
│     注文API │                                        │ 入ってくる: 2 │
│     在庫    │                                        │ 出ていく:   3 │
│   ▸ 在庫    │                                [ミニマップ]│ 通る流れ: 注文 │
└────────────┴────────────────────────────────────────┴──────────────┘
```

- **目次**: ノードの階層をツリーで表示。クリックでその階層へ。今いる場所を強調
- **URL**: `#/order/order.api` のように階層と選択中のノードを持つ。ブラウザの戻る・進むで階層を行き来でき、リンクで共有できる
- **検索**: ラベル・`sub`・`tags`・`detail` の文字で探して、その階層へ飛ぶ
- **データで絞り込み**: `data` を選ぶと、そのデータが流れる矢印だけを強調 (「個人情報はどこを通る？」)
- **詳細パネル**: `detail` の HTML をそのまま出せる (表・コード・画像も可)。入ってくる・出ていく矢印と、通るデータの流れの一覧を自動で付ける
- **印刷・PDF**: 階層ごとに 1 ページ (図 + そのノードの詳細) を、目次の順に書き出す
- 画面幅が狭いとき (スマートフォン): 目次と詳細パネルは引き出し式

### 5.3 ファイル形式

```
<head>  <meta name="jh-kind" content="map"> / jh-theme / jh-brand / <title>
<!-- jh:map -->          … マップのデータ (JSON。編集してよい)
<!-- jh:deck-style -->   … 専用 CSS (編集してよい)
===== 自動生成 =====     … エンジン・テーマ・ブランド (編集しない)
<!-- jh:deck-script -->  … 専用 JS (編集してよい)
```

- 作成: `npm run new -- <name> "タイトル" --kind map` (`decks/YYYY-MM-DD-<name>.html`)
- `npm run upgrade` / `npm run pdf` / MCP の `read_deck` `write_deck` `audit_deck` `screenshot_deck` は `jh-kind` を見て切り替える
- 検査: `Map.audit()` (存在しない id への矢印、流れの途切れ、1 階層のノード数、ラベルのはみ出し)
- スライドの `.diagram` とマップ文書は **同じ JSON** を使う。マップ文書の一部 (ある階層から下) をスライドに貼る、またはその逆ができる (MCP に `copy_map_part` を追加)

## 6. ER 図を同じ仕組みに載せる

ER 図も「階層 + 矢印 (関連)」なので、同じ描画部品の別の見た目として扱う。

| 階層 | 見えるもの | 矢印 |
|---|---|---|
| 0: 業務領域 | 会員・注文・在庫・商品 などのまとまり | 領域の間の関連 (本数を集約表示) |
| 1: テーブル | 領域の中のテーブル (列は主キー・外部キーだけ) | 外部キー (`N:1` など) |
| 2: テーブル詳細 | すべての列・インデックス・サンプルデータ (`detail`) | — |

```jsonc
{
  "view": "er",
  "nodes": [
    { "id": "order", "label": "注文", "children": { "nodes": [
      { "id": "orders", "kind": "table", "columns": ["id PK bigint", "user_id FK bigint", "status varchar"] },
      { "id": "order_items", "kind": "table", "columns": ["id PK bigint", "order_id FK bigint", "item_id FK bigint"] }
    ] } },
    { "id": "member", "label": "会員", "children": { "nodes": [
      { "id": "users", "kind": "table", "columns": ["id PK bigint", "name varchar"] }
    ] } }
  ],
  "relations": [
    { "from": "orders.user_id", "to": "users.id", "card": "N:1" }   // 今の .er-diagram と同じ書き方
  ]
}
```

- `relations` は列単位で書き、上の階層では `注文 ── 会員` に集約される (2.3 と同じルール)
- 今の `.er-diagram` (1 階層・6 テーブルまで) はそのまま残す。テーブルが多いときはこちらを使う

### システムとデータをつなぐ (発展)

システム関連図の矢印の端に、テーブルを指定できるようにする。

```jsonc
{ "from": "order.api", "to": "orders", "type": "write" }   // to がテーブル
```

これで、**テーブルを選ぶと「このテーブルを読む・書く機能」**、**機能を選ぶと「この機能が触るテーブル」**が両方向に出る (CRUD 表の代わり)。
1 つのマップ文書に、システムの見方 (`view: system`) とデータの見方 (`view: er`) を切り替えるタブを付ける。

## 7. 状態遷移図を同じ仕組みに載せる

| 対応 | 階層マップ |
|---|---|
| 状態 | `kind: "state"` のノード (初期状態 `initial: true`、終了 `final: true`) |
| 遷移 | 矢印。`label` にイベント、`guard` に条件、`action` に処理 |
| 入れ子の状態 (複合状態) | `children` (中に入ると内部の状態遷移) |

- `"simulate": true` で、今の状態を光らせ、出ていく遷移をボタンとして並べる。クリックで遷移し、履歴を説明バーに残す (第 2 弾デッキの「状態遷移図を遷移させて確かめる」を部品にする)
- 遷移できない状態 (どこからも来ない・どこへも行けない) を `audit` で警告する

## 9. 決めておきたいこと

1. **矢印をどこに書くか**: 「一番細かい階層で書いて上は自動」を基本にする案。上の階層だけ書いて中身は後で、という書き方も許すか (許す場合、その矢印は中に入ると境界ノードにつながる)
2. **マップ文書をデッキと同じ `decks/` に置くか**、`maps/` のように分けるか
3. **大きなマップを 1 ファイルの JSON に全部書くか**: 100 ノードを超えると AI が一度に読み書きするには重い。MCP に「1 つの階層だけ読む・書く」道具 (`read_map_level` / `write_map_level`) を用意する案
4. **手で配置を直せるようにするか**: 自動配置を基本にし、マップ文書の上でノードをドラッグすると `x` / `y` を保存する (Ctrl+S) 案
